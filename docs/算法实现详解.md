# 算法实现详解:从 ItemCF / MF 到 BPR-MF

> 目标读者:有 Java 后端/CRUD 经验、第一次接触推荐系统的人。
> 建议读法:打开源码对着看。本文所有 `文件:行号` 都可以直接跳转;数学公式只讲"这一步在代码里对应哪一行",不展开证明。
> 本文档覆盖阶段一(ItemCF + 评分 MF)与阶段二(BPR-MF 隐式反馈排序)。

---

## 0. 先摆正坐标:推荐系统在干什么

CRUD 的心智是"给定 ID → 查/改一条记录,对错二元"。推荐系统的心智是:

> 给定一个用户(和上下文)→ 给整个候选物品集合打分 → 排序 → 取前 K 个。
> 没有"正确答案",只有统计指标;模型是"估计器",不是"查询器"。

阶段一的两个算法,恰好覆盖两种截然不同的"打分"哲学:

| | ItemCF | 矩阵分解 MF |
|---|---|---|
| 打分依据 | **数出来**的:共同用户多的物品更相似 | **学出来**的:用梯度下降拟合一个低维隐空间 |
| 需要训练吗 | 几乎不用(统计共现即可) | 需要,迭代优化 |
| 擅长 | 召回 / Top-N 排序 | 评分预测(也能排序) |
| 单次打分复杂度 | O(用户的 topK 邻居) | O(隐维度 k) |
| 本质 | 记忆型(memory-based) | 模型型(model-based) |

理解这张表,就理解了这场"从统计到学习"的演进。阶段二则在 MF 的基础上,把"评分预测"彻底改成"排序学习"。下面逐个拆。

## 1. 共享地基:倒排索引与统一接口

两个算法都建立在同一层抽象上,先花两分钟看懂它,后面会一直复用。

### 1.1 `Dataset`:`src/main/java/tour/recsys/data/Dataset.java`

CRUD 里你可能习惯"有一个 `ratings` 表,要查就 `where user_id=?`"。推荐系统里这样查会慢到不可用,所以 `Dataset` 在构造时就把索引建好:

- `byUser`:userId → 该用户的所有评分(`ratingsOfUser`)
- `byItem`:movieId → 该物品的所有评分(`ratingsOfItem`)
- `globalMean`、`maxTimestamp` 等派生量

**为什么重要**:ItemCF 要"哪些用户评过这部电影",MF 要"某用户评过什么"——都是高频查询。提前建索引把查询从 O(N) 降到 O(结果数)。这是你熟悉的"以空间换时间",只是对象换成了推荐数据。

`itemsOfUser(userId)` 返回 `Set<Long>`,后面评估时的"已见物品要去掉"就靠它。

### 1.2 `Recommender` 接口:`src/main/java/tour/recsys/model/Recommender.java`

```java
List<Long> recommend(long userId, int topN, Set<Long> exclude);
```

三个参数就是推荐系统的通用签名:**给谁、要几条、排除什么**。`exclude` 通常是用户训练集里已交互过的物品(而且线上还要排除已曝光的,这涉及位置偏置,阶段三再谈)。

**设计意图**:所有算法实现同一个接口,`Main` 和 `Evaluation` 就能对它们一视同仁地跑评估、出对比表。你新增 BPR、DIN 都只要实现这个方法,评估代码一行不用改。这是"面向接口"在算法迭代里的价值——**让不同算法可比较**。

## 2. ItemCF:物品协同过滤

源码:`src/main/java/tour/recsys/model/ItemCF.java`

### 2.1 直觉(先别看公式)

你看过《玩具总动员》,系统发现"看过《玩具总动员》的人大多也看了《虫虫危机》",于是把《虫虫危机》推给你。**两个物品被同一批用户喜欢,它们就相似** —— 就这么简单。

注意它推荐的是**物品**,不是"和你相似的人用了什么"。这是 ItemCF 和 UserCF 的分水岭,而工业界更爱 ItemCF,原因在 2.5 节。

### 2.2 数学:余弦相似度

把每个物品表示成一个"用户集合":

```
U_i = 喜欢物品 i 的用户集
```

两个物品的相似度用集合的**余弦相似度**:

```
sim(i, j) = |U_i ∩ U_j| / sqrt(|U_i| · |U_j|)
```

- 分子 `|U_i ∩ U_j|`:同时喜欢 i 和 j 的用户数(两者"共现"的次数)。
- 分母 `sqrt(|U_i|·|U_j|)`:归一化,防止"热门物品和谁都有共同用户"导致相似度虚高。

给用户 u 推荐时,拿他历史喜欢的每个物品 i,把 i 的相似物品的相似度**累加**到候选物品上:

```
score(u, c) = Σ_{i ∈ I_u} sim(i, c)
```

分数最高的若干物品就是推荐结果。**这就是"召回/排序"里打分的雏形**:候选集 = 历史物品的相似物品,分数 = 相似度累加。

### 2.3 三个工程决策(这才是实现的重点)

公式谁都能写,能跑在 10 万条数据上才是本事。代码里有三处关键取舍:

**(1) 用倒排索引两两配对,而不是物品两两盲扫** —— `ItemCF.java:57-69`

朴素做法是"对任意两个物品算相似度",复杂度 O(items²) = 9724² ≈ 9500 万对,大部分是 0(没有共同用户),纯浪费。

正确做法:**遍历每个用户评过的物品,两两配对累加共现次数**。复杂度变成 O(Σ_u |I_u|²)——只看真实存在共现的对。代码里 `coCount` 就是"共现次数矩阵"的稀疏表示(`Map<物品, Map<物品, 次数>>`)。

> 这是整个 ItemCF 最核心的一行工程直觉:**从"问所有物品对"改成"问所有用户"**。你的数据是稀疏的,就让循环只走非零的部分。

**(2) 只保留每个物品的 topK 邻居** —— `ItemCF.java:71-88`

一个热门片可能和上万个物品有共现。全存下来,`sim` 会爆炸,而且长尾邻居多是噪声。所以每个物品只留最相似的 `topKNeighbors` 个(`ItemCF.java:84`)。这既省内存,又天然过滤噪声。

**(3) 热门惩罚(相似度收缩)** —— `ItemCF.java:79`

```java
double shrink = 1.0 / (1.0 + popAlpha * (itemNorm.get(j) - 1.0));
```

`itemNorm.get(j)` 是 `sqrt(|U_j|)`。想法是:越热门的物品,相似度打越狠的折,避免"因为热门被所有人看了"就误判为相似。

**但这里的公式量纲是错的** —— 详见第 5 节的踩坑复盘。当前默认 `popAlpha=0`,即关掉惩罚。这段代码留作"实验旋钮",不是"开箱即用"。

### 2.4 推荐阶段:代码逐段走查

`recommend` 在 `ItemCF.java:91-118`,四步:

1. `ItemCF.java:93-96` 取出该用户的历史物品;没有历史就返回空(冷启动,阶段一不处理)。
2. `ItemCF.java:97-110` 遍历历史物品,把每个邻居的相似度累加到 `score`。**注意 `ItemCF.java:105`**:累加前先按 `exclude` 过滤掉用户已看过的,避免推荐已经看过的电影。
3. `ItemCF.java:111-112` 对候选按分数降序排序。
4. `ItemCF.java:113-117` 截取前 topN。

有一个容易被忽略的细节:为什么第 2 步不会推荐"用户自己历史的物品"?因为相似度矩阵里 `sim(i,i)` 不存在(co-count 只记录 i≠j 的对),加上 `exclude` 兜底。**这个"不自指"性质是 ItemCF 的结构保证**,不需要额外去重。

### 2.5 为什么工业界偏爱 ItemCF 而不是 UserCF

- **物品比用户稳定**。商品一旦上架，它的相似关系相对固定,可以离线算好、缓存,在线只查表;而用户兴趣天天变,UserCF 的邻居要频繁重算。
- **可解释**。"因为你看过 A、B" → 推荐 C,理由明确。
- **复杂度更友好**。物品数通常远小于用户数,相似度矩阵规模可控。

代价:ItemCF 依赖**较强的共现**,数据极度稀疏(长尾物品没人一起看)时会失效。这时就需要 MF 这种"泛化"能力更强的模型。

### 2.6 复杂度小结

| 阶段 | 复杂度 | 说明 |
|---|---|---|
| 训练 | O(Σ_u |I_u|²) | 配对共现;ml-latest-small 上毫秒级 |
| 训练 | O(#items · avgNeighbors · log) | 邻居排序取 topK |
| 单次推荐 | O(|I_u| · topK) | 只碰历史物品的邻居,与全量物品数无关 |

**最后一行的意义**:ItemCF 的单次推荐**不随物品总数线性增长**,这正是它适合做**召回**的原因。记住这一点,和 MF 对比时会有惊喜。

## 3. 矩阵分解 MF:从"数"到"学"

源码:`src/main/java/tour/recsys/model/MatrixFactorization.java`

### 3.1 为什么要"学"

ItemCF 的相似度是**统计**出来的:有共现才有相似度,没共现就是 0。问题是真实数据极度稀疏(610 用户 × 9724 物品,只有 10 万条评分,密度约 1.7%),绝大多数物品对没有共现,ItemCF 束手无策。

**MF 的思路**:假设每个用户和每个物品都能用一个 k 维向量("隐向量")描述,用户对物品的喜好 = 两个向量的**内积**。即使某个用户和某个物品从没一起出现过,只要它们的隐向量方向相近,就能预测出高分——这就是**泛化**。

隐向量的维度对应什么?没人能确切解释,但经验上它可能编码了"是否偏爱 90 年代动作片""对文艺片的容忍度"这类潜在因子。**"隐"就是"不直接可观测"的意思。**

### 3.2 模型公式

```
r̂_ui = μ + b_u + b_i + p_u · q_i
```

| 符号 | 含义 | 直觉 |
|---|---|---|
| μ | 全局平均分 | "所有人都打 3.5 分"的基线 |
| b_u | 用户偏置 | 这人打分天生苛刻(负)还是宽容(正) |
| b_i | 物品偏置 | 这电影公认好(正)还是烂(负) |
| p_u | 用户隐向量(k 维) | 这个人的偏好画像 |
| q_i | 物品隐向量(k 维) | 这个物品的属性画像 |

**为什么要有 μ、b_u、b_i?** 因为内积 `p_u·q_i` 太"干净",它学不会"某用户就是爱打高分"这种与物品无关的偏移。加上偏置项后,内积只需要负责"个性化"部分,收敛大大加速。这是 Koren 2009 那篇论文的核心贡献之一(参考 §6)。

对应代码:`MatrixFactorization.java:94` —— `mu + bU[u] + bI[i] + dot(p[u], q[i])`。

### 3.3 损失函数与 SGD 更新(逐行推导)

**目标**:让预测分逼近真实分,同时防止隐向量过大(过拟合):

```
L = Σ_{(u,i) ∈ 已观测} (r_ui − r̂_ui)²  +  λ(‖p_u‖² + ‖q_i‖² + b_u² + b_i²)
```

第一项:拟合误差。第二项:正则(λ = 代码里的 `reg`),压制参数大小。

**优化方法:随机梯度下降(SGD)**。每次只看一条评分,算出误差 `e = r_ui − r̂_ui`,然后让每个参数沿"让误差变小"的方向走一小步。对上面的损失逐参数求偏导,得到四条更新式(**这就是代码 `MatrixFactorization.java:96-104`**):

```
e_ui = r_ui − (μ + b_u + b_i + p_u·q_i)

b_u ← b_u + η(e_ui − λ b_u)          // η = 学习率 lr
b_i ← b_i + η(e_ui − λ b_i)
p_u ← p_u + η(e_ui · q_i − λ p_u)
q_i ← q_i + η(e_ui · p_u − λ q_i)
```

三个容易写错的细节:

1. **`p_u` 和 `q_i` 必须用彼此的"旧值"更新**。看 `MatrixFactorization.java:101-104`:先把 `pu[f]`、`qi[f]` 存进局部变量 `puf`、`qif`,再用它们算彼此的梯度。如果先更新了 `p_u` 再去更新 `q_i`,就用到了"被污染"的值,SGD 会跑偏。这是手写 MF 最经典的 bug。
2. **正则项只压当前参数,不碰误差项**。`− reg * puf` 而不是 `- reg * (e*puf)`。
3. **偏置和隐向量用同一个 η 和 λ**(可分开调,但阶段一从简)。

### 3.4 训练流程:代码逐段走查

`fit` 在 `MatrixFactorization.java:54-108`,五步:

1. **建索引** `MatrixFactorization.java:55-67`:把稀疏的 `long` userId/movieId 映射成紧凑的 `0..n-1` 下标。为什么要做?因为接下来要把参数存进 `double[]`/`double[][]` **数组**——数组用连续内存 + 下标访问,比 `HashMap<Long, double[]>` 快一个数量级。这是"离线训练要用数组、在线服务才用 Map"的典型分工。
2. **分配参数** `MatrixFactorization.java:68-71`:`bU[nu]`、`bI[ni]`、`p[nu][k]`、`q[ni][k]`。
3. **随机初始化** `MatrixFactorization.java:73-83`:隐向量用均值 0、标准差 `INIT_STD=0.01` 的高斯分布初始化。**为什么要随机且小?** 全 0 初始化会让所有隐向量永远同向(对称性无法打破);太大则初期预测剧烈震荡。
4. **缓存历史** `MatrixFactorization.java:84-86`:仅用于 `recommend` 的兜底判断。
5. **SGD 主循环** `MatrixFactorization.java:88-107`:每个 epoch 先 `shuffle`(打乱顺序,避免"按用户/物品排序的评分"引入相关性导致收敛慢或震荡),再逐条评分更新参数。

### 3.5 参数速查

| 参数 | 代码位置 | 含义 | 阶段一取值 | 调大的后果 |
|---|---|---|---|---|
| `k` | 构造器 | 隐向量维度 | 100 | 表达力↑,内存/时间↑,过拟合风险↑ |
| `epochs` | 构造器 | 遍历全量数据次数 | 50 | 拟合更充分,过多则过拟合 |
| `lr` (η) | 构造器 | 每步走多远 | 0.01 | 太大不收敛,太小训不动 |
| `reg` (λ) | 构造器 | 正则强度 | 0.02 | 太大会把隐向量压平(见 §5.2) |

### 3.6 关键认知:MF 为什么排序弱?

看 `recommend`(`MatrixFactorization.java:131-152`)——它要给**每个未交互物品**算一次分,复杂度 **O(物品数 × k)**。610 用户 × 9724 物品 × 100 维 = 每次评估约 6 亿次浮点运算。**这个复杂度决定了 MF 不适合做全量召回,只适合做候选集上的精排。**

但更深层的问题在**目标函数**:MF 最小化的是**已观测评分**的平方误差,它从来没见过"负样本"(用户没评分的物品,可能是没看到,也可能是讨厌)。所以它在排序未观测物品时区分度很差——这就是阶段一的实测结果:MF 的 RMSE 从 1.13 降到 0.97(预测确实准了),但 HR@10 只有 0.0197,远低于 ItemCF。

**"评分预测准"≠"排得靠前",这是推荐系统最经典的认知鸿沟**,也是阶段二用 BPR 成对损失要解决的目标错配。

## 4. 评估层:为什么是这三个指标

源码:`src/main/java/tour/recsys/eval/Metrics.java`、`Evaluation.java`

先看**切分**:`TrainTestSplitter.leaveOneOut`(`data/TrainTestSplitter.java`)——每个用户按时间留最新一条作测试。为什么不留随机一条?因为线上要预测的就是"用户接下来会喜欢什么",留最新的最接近真实场景,也是该领域标准做法(留出的那条真实物品,就是排序要命中的目标)。

三个指标各管一件事:

- **HR@K(Hit Ratio@K)** `Metrics.java:35-38`:命中就 1,否则 0。leave-one-out 下每用户只有 1 个相关物品,此时它等价于 Recall@K。**回答"有没有排进前 K"。**
- **NDCG@K** `Metrics.java:45-51`:单个相关物品时,排在位置 r 得 `1/log₂(r+1)`。**回答"排得够不够靠前"**。HR 说"进前 10 就行",NDCG 说"进第 1 和第 10 不一样"。
- **RMSE** `Metrics.java:53-62`:预测分与真实分的均方根误差,是 MF 这种评分预测模型的主指标。**回答"分数预测准不准"**。

补一个**覆盖率**(`Evaluation.java:36-48`):"被推荐过的不同物品数 / 总物品数"。它防的是"所有用户都被推同样的 10 部热门片"——Popular baseline 覆盖率只有 1.3%,一看就知道是"偷懒"的推荐。

**为什么必须同时看这几条**:单看 HR 会被热门基线骗(反正热门片总有人会点),单看 RMSE 会漏掉排序能力(§3.6),单看精度会漏掉多样性(全推爆款)。**离线评估永远是"多指标权衡",没有单一数字能说明推荐系统好不好。**

## 5. 踩坑复盘(阶段一最有价值的部分)

这两个坑不是"写错了",而是**参数/目标的量纲与错配**,值得单独记住。

### 5.1 热门惩罚量纲用错,把 ItemCF 召回清零

`popAlpha` 默认设成 10 时,**HR@10 = 0.0000**,比什么都不做的 Popular(0.0410)还差。参数扫描:

| alpha | topK | HR@10 | 覆盖率 |
|---|---|---|---|
| **0.0** | 50 | **0.0541** | 4.5% |
| 0.5 | 50 | 0.0000 | 8.3% |
| 1.0 | 50 | 0.0016 | 2.9% |
| 10.0 | 200 | 0.0000 | 1.7% |

**根因**:`shrink = 1/(1 + alpha·(sqrt(n_j) − 1))`(`ItemCF.java:79`)。`n_j` 是物品被评分次数,热门片能到几百,`sqrt(n_j)` 仍达 ~17,乘上 alpha 后分母爆炸成上百倍。结果**只有"极少人评过"的冷门片能拿到非零相似度**,模型永远只推冷门噪声,留出的热门片一条不命中。

**教训**:任何"惩罚/归一化"项,先算清它的**取值范围**再定系数。一个系数就能把信号全压没。经验做法是先关掉(`alpha=0`)看基线,再逐步加、每步看指标。

### 5.2 正则越强 RMSE 越好看,但排序能力归零

| reg | RMSE | HR@10 |
|---|---|---|
| 0.00 | 0.9896 | 0.0197 |
| 0.02 | 0.9664 | 0.0197 |
| 0.05 | 0.9556 | 0.0082 |
| 0.10 | 0.9567 | 0.0000 |

**根因**:正则把隐向量 `p_u`、`q_i` 压向 0,模型退化成"只用 μ + b_u + b_i 的偏置模型"。偏置模型预测"安全"(评分总在均值附近),RMSE 好看;但它**丢掉了所有个性化排序信号**,HR 归零。

**教训**:离线指标的"最优"取决于你优化哪个目标。调参时永远盯着你真正要的指标,别被一个好看的 RMSE 骗进"上线后毫无个性化"的坑。

## 8. 阶段二:BPR-MF 与隐式反馈排序

源码:`src/main/java/tour/recsys/model/BprMF.java`、`src/main/java/tour/recsys/Main.java`

阶段二要解决的问题,在 §3.6 已经埋好了伏笔:**MF 评分预测准,但 Top-N 排序弱**。原因是 MF 的损失函数只盯着"已观测评分的误差",从来没学过"我喜欢的 > 我不喜欢的"这个排序关系。

BPR(Bayesian Personalized Ranking)把目标彻底换了:不预测分数,只学习排序。

### 8.1 从"显式评分"到"隐式反馈"

真实业务里,用户很少主动打分;更多的是点击、浏览、播放、购买——这些叫**隐式反馈**(implicit feedback)。隐式反馈只有"交互了"和"没交互"两种状态,没有"打 5 分还是 2 分"的细粒度。

MovieLens 是显式评分数据集(0.5~5.0),阶段二把它转成隐式正样本:

```java
Dataset implicit = all.filterRatings(4.0);  // Main.java:36
```

规则:**评分 ≥ 4.0 视为"喜欢"(正样本),其余忽略**。为什么选 4.0?因为 5 分制里 4、5 分通常代表明确的正面态度,3 分及以下更接近"无感/不喜欢"。

数据变化:

```
原始评分:              610 用户, 9724 物品, 100836 条评分
隐式正样本(>=4.0):     609 用户,  6298 物品,  48580 条交互
```

物品数从 9724 降到 6298,因为大量低分/冷门电影被过滤掉了。**这是业务侧最重要的变化:推荐的目标从"预测用户会打几分"变成"猜用户会不会喜欢"**。

### 8.2 BPR 的核心思想:正样本要排在负样本前面

对每一个观测到的正样本 `(u, i)`,BPR 问:

> 用户 u 对物品 i 的偏好,应该高于他对任意一个他没交互过的物品 j 的偏好。

用符号写就是:

```
x_ui  >  x_uj
```

`x_ui` 是模型给用户 u、物品 i 打的"偏好分数",和阶段一 MF 的预测分类似,但不再有"评分"的含义。

**关键:我们不直接优化"x_ui 等于几",而是优化"x_ui 比 x_uj 大多少"**。

### 8.3 负采样:从"没交互"里构造负样本

用户没交互过的物品成千上万,不可能把它们全部拿来比较。BPR 的做法是**负采样**(negative sampling):对每个正样本 `(u,i)`,随机抽几个用户没见过的物品 `j` 当负样本。

代码:`BprMF.java:96-103`

```java
for (int s = 0; s < negSamples; s++) {
    int j;
    do {
        j = rnd.nextInt(nItems);
    } while (hist.contains(itemIds[j]));
    update(u, i, j);
}
```

- `negSamples=5`:每个正样本配 5 个负样本。
- `hist` 是该用户在训练集里交互过的物品集合,负采样必须排除这些,否则会把正样本错当成负样本。
- 均匀随机采样:所有没交互过的物品概率相同。这是最简单的做法;工业界会用"按 popularity 加权"或"hard negative"等更复杂的策略,但阶段二先把基线跑通。

**一个具体例子**:假设用户 414 训练集里喜欢过《玩具总动员》《星球大战》《教父》。对正样本《星球大战》,负采样可能抽到《西雅图夜未眠》《勇敢者的游戏》《某部冷门纪录片》——这些就是他"没看过"的电影,模型要学到《星球大战》的分数高于它们。

### 8.4 BPR 损失函数与 SGD 更新

我们要让 `x_ui - x_uj` 尽量大。BPR 用 sigmoid 把它变成概率:

```
P(i >_u j) = σ(x_ui - x_uj) = 1 / (1 + exp(-(x_ui - x_uj)))
```

如果 `x_ui` 比 `x_uj` 大很多,这个概率接近 1,说明模型"很有信心 i 应该排在 j 前面"。BPR 的目标就是最大化这个概率(等价于最小化负对数似然)。

代码里 `x_ui` 只保留了物品偏置和隐向量点积(没有全局均值和用户偏置):

```java
// BprMF.java:109
x_ui = bI[i] + p[u] · q[i]
x_uj = bI[j] + p[u] · q[j]
z    = x_ui - x_uj = (bI[i] - bI[j]) + p[u] · (q[i] - q[j])
```

注意这里没有 `μ` 和 `b_u`:因为排序只关心"相对高低",全局均值和用户偏置对任意物品都一样,相减就抵消了。保留 `bI` 是因为不同物品的"热门程度"确实影响排序。

损失对参数的梯度推出来后,得到 `BprMF.java:108-127` 的更新:

```java
double sigmoidNeg = 1.0 / (1.0 + Math.exp(z));  // = 1 - σ(z)

bI[i] += lr * ( sigmoidNeg - reg * bI[i]);
bI[j] -= lr * ( sigmoidNeg - reg * bI[j]);

pu[f] += lr * (sigmoidNeg * (qif - qjf) - reg * puf);
qi[f] += lr * (sigmoidNeg *  puf        - reg * qif);
qj[f] -= lr * (sigmoidNeg *  puf        - reg * qjf);
```

`sigmoidNeg` 的含义:"模型认为 i 应该比 j 高,但实际差距是 z,我错得有多狠"。

- `sigmoidNeg` 接近 1 → `z` 很小(甚至为负),模型严重搞错,要大力更新。
- `sigmoidNeg` 接近 0 → `z` 已经很大,模型很有信心,更新幅度小。

梯度方向很直观:

- `p_u` 向 `q_i` 靠近,向 `q_j` 远离。
- `q_i` 向 `p_u` 靠近;`q_j` 向 `p_u` 远离。
- `bI[i]` 增大,`bI[j]` 减小。

这就是 BPR 的"拉扯":**把用户向量拉向喜欢的物品,推离不喜欢的物品**。

### 8.5 为什么 BPR 的排序能比评分 MF 强

阶段一 MF 的损失是 `(真实分 - 预测分)²`,它的"世界"里只有"已评分的格子"。用户没评分的电影对它来说是透明的,模型从没被告诉"这些应该排在后面"。

BPR 的损失是 `log(1 + exp(-(x_ui - x_uj)))`,它的"世界"里天然有成对的"正样本在上、负样本在下"。**每一个负样本都在告诉模型:这些没交互过的物品不应该排这么高**。

结果:

| 模型 | HR@10 | NDCG@10 | 覆盖率 |
|---|---|---|---|
| Popular | 0.0295 | 0.0149 | 1.0% |
| ItemCF | 0.0396 | 0.0186 | 10.8% |
| **BPR-MF(k=100)** | **0.0438** | **0.0205** | **15.3%** |

BPR-MF 超过了 ItemCF,而且覆盖率也更高(不会只推热门片)。这就是"目标函数对准了任务"带来的收益。

### 8.6 阶段二的两个关键超参

| 参数 | 代码位置 | 含义 | 阶段二取值 | 影响 |
|---|---|---|---|---|
| `negSamples` | `BprMF` 构造器 | 每个正样本配几个负样本 | 5 | 太少学不稳,太多训练慢；通常 1~10 |
| `filterRatings` | `Main.java:36` | 几分以上算正样本 | 4.0 | 阈值越高正样本越"纯净"；太低会把无感样本混进来 |

`negSamples=5` 意味着训练数据量被放大了 5 倍(每个正样本产生 5 对比较),所以 BPR 训练比阶段一 MF 慢。`Main.java` 里记录了训练耗时约 2.1s(ml-latest-small 上)。

### 8.7 切分方式的变化:从 leave-one-out 到 time-split

阶段一用 leave-one-out(每个用户只留最新 1 条作测试),阶段二改成 `timeSplit(0.2, 5)`:每个用户按时间排序,前 80% 训练、后 20% 测试。

```java
TrainTestSplitter.Split split = TrainTestSplitter.timeSplit(implicit, 0.2, 5);  // Main.java:44
```

为什么换?因为隐式反馈下每个用户可能有很多条交互,只留 1 条测试指标方差大;time-split 每用户留多条,评估更稳定。`Evaluation.java:37-41` 也改成对每用户的多个测试物品分别算 HR/NDCG 再取平均。

### 8.8 阶段二踩坑:把"所有评分"当正样本,BPR 反而更差

一开始没有 `filterRatings(4.0)`,直接把全部 10 万条评分当隐式正样本训练 BPR,结果 HR@10 只有 2.46%,还不如 ItemCF。

**根因**:3 分、2 分甚至 0.5 分的评分,对用户来说未必是"喜欢"。把它们当正样本,等于告诉模型"用户喜欢《某烂片》",负采样时再随便抽个没看过的电影说"这个不如《某烂片》"。标签本身就脏了,模型当然学不好。

**教训**:隐式反馈的"正样本定义"是业务问题,不是技术问题。MovieLens 里用 ≥4.0 当"喜欢"是领域惯例,但真实业务里可能需要结合播放完成率、停留时长、是否收藏等行为来定义。

### 8.9 BPR-MF 的局限

- 仍然是 O(物品数 × k) 的打分复杂度,**适合做候选集精排,不适合全量召回**。
- 冷启动问题依旧:新用户/新物品没有向量,只能退化成热门推荐。
- 均匀负采样假设"没交互 = 不喜欢",但很多时候"没交互 = 没看到",会引入偏差。阶段三可以引入更复杂的采样策略。

## 9. 下一步(阶段三)

阶段二证明了"换目标函数"的威力。阶段三可以朝两个方向扩展:

1. **召回 + 精排的两级架构**:先用 ItemCF/ANN 做候选召回,再用 BPR-MF 做 Top-K 精排,解决 BPR-MF 全量打分慢的问题。
2. **更真实的隐式反馈建模**:引入点击/曝光日志、处理位置偏置、尝试 WARP/hard negative 等更难的负采样。
3. **模型并行与工程化**:把训练好的 `p`/`q` 导出成向量服务,用向量检索(如 Faiss/HNSW)做线上推荐。这是从"算法玩具"走向"推荐系统服务"的关键一步。
