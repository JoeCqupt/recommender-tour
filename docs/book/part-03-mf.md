## 0. 诞生:一场 100 万美元的比赛

2006 年,Netflix 悬赏 **100 万美元**,要求把电影推荐准确度提升 10%。三年后夺冠的团队核心武器就是**矩阵分解**。

这件事的革命性在哪?

- **之前的主流是"邻居法"**(像第 2 部的 ItemCF):靠"看过 A 的人也看了 B"这种**统计共现**来推荐。
- **MF 第一次系统地用"学习参数"**:不数共现,而是**假设一个规律、解出规律**。

所以 MF 是推荐系统从"统计时代"迈向"机器学习时代"的分水岭。你学的不是一道数学题,是一次范式转变。

## 1. 问题本身:一张满是窟窿的 Excel 表

想象一张巨大的表格:

| | 星际穿越 | 泰坦尼克 | 战狼 |
|---|---|---|---|
| 你 | 5 | ? | ? |
| 甲 | 4 | 3 | ? |
| 乙 | ? | ? | 5 |

- 行 = 用户,列 = 电影,格子里 = 打分;
- 真实世界里这张表可能有 **上亿个格子**,但用户只填了 **1%**,剩下 99% 是空的。

**推荐的任务就是:猜出这些空格子里他会打几分,然后把分最高的那些挑出来推给他。**

两种世界观:

- **ItemCF 的看法**:空格子不会凭空出现,我看"填过的格子"里谁和谁总一起出现。
- **MF 的看法**:别管邻居了。我赌这张表背后藏着一个简单规律。只要我把规律找出来,空格子自然能算出来。

MF 赌的是什么规律?下一节揭晓。

---

## 2. 核心思想:把人和电影放进同一个"品味空间"

### 2.1 地图上的坐标

假设每个人心里都有几条**隐藏的口味轴**,比如:

- 轴 1:爱"动作 / 刺激" ↔ 爱"文艺 / 慢节奏"
- 轴 2:爱"烧脑 / 深奥" ↔ 爱"轻松 / 娱乐"

于是:

- 每一部电影可以标一个坐标,比如《战狼》= `[0.9, 0.2]`(很动作,不太烧脑);
- 每一个用户也可以标一个坐标,比如你 = `[0.9, 0.1]`(超爱动作,不爱烧脑)。

**一个人会不会喜欢一部电影 ≈ 这两个坐标"对不对得上"。**

怎么算"对得上"?用**点积**:

```
你喜欢《战狼》的程度 = 你的坐标 · 电影的坐标
                     = 0.9×0.9 + 0.1×0.2 = 0.83  → 高分,该推
你喜欢《文艺片》的程度 = 0.9×0.1 + 0.1×0.9 = 0.18  → 低分,不推
```

坐标**方向越一致,点积越大**,就代表越匹配。这就是"品味空间里的门当户对"。

### 2.2 相亲比喻

把用户和电影想成两拨参加相亲的人:

- 每个人有一份"属性清单"(坐标);
- 两人的清单越般配,总分越高。

MF 就是**从"已有的几桩成功/失败的相亲记录"里,反推出每个人的属性清单**。

### 2.3 为什么能补洞

回到那张带洞的评分表 **R**(用户数 × 电影数)。MF 说:

```
R ≈ P × Qᵀ
```

- **P**:用户数 × k 的矩阵,第 u 行就是用户 u 的坐标;
- **Q**:电影数 × k 的矩阵,第 i 行就是电影 i 的坐标;
- 用户 u 对电影 i 的预测分 = P 的第 u 行 · Q 的第 i 行。

```
        R (用户×电影, 大量空格)      ≈      P (用户×k)   ×   Qᵀ (k×电影)
       ┌─────────────┐                  ┌────────┐      ┌────────┐
   你  │ 5  ?  ?  ... │                  │ 0.9 0.1│      │ 0.9 0.1│ ←《战狼》
   甲  │ 4  3  ?  ... │        ≈         │ 0.2 0.8│  ×   │ 0.1 0.9│ ←《文艺片》
   乙  │ ?  ?  5  ... │                  │ 0.5 0.5│      └────────┘
       └─────────────┘                  └────────┘
       一亿个格子                        每个用户只要      每部电影只要
       (99% 是空的)                      k 个数            k 个数
```

**为什么这叫"分解"?** 原本是一个又大又稀的矩阵,现在被拆成两个又瘦又密的矩阵相乘。**信息被压缩了。**

**为什么压缩能"补洞"?** 因为压缩的前提是"这张表有内在的简单结构"。一旦模型抓住了这个结构,任何空格子都可以用 `P行 · Q行` 算出来。这就是 MF 能推荐"你没评价过的电影"的原理。

## 3. 模型公式:三块拼图

```
r̂_ui = μ + b_u + b_i + p_u · q_i
```

| 符号 | 含义 | 直觉 |
|---|---|---|
| μ | 全局平均分 | "所有人都打 3.5 分"的基线 |
| b_u | 用户偏置 | 这人打分天生苛刻(负)还是宽容(正) |
| b_i | 物品偏置 | 这电影公认好(正)还是烂(负) |
| p_u | 用户隐向量(k 维) | 这个人的偏好画像 |
| q_i | 物品隐向量(k 维) | 这个物品的属性画像 |

> **🔤 公式翻译**
> - **读作**:"预测分 = 平均分 + 这个人的偏差 + 这个物品的偏差 + 这个人的口味和这个物品属性的匹配度"。前两项负责"大众水平",最后一项 `p_u·q_i` 才是个性化部分。
> - **没见过的符号**:`r̂`(念 r-hat)="预测值",帽子 `^` 在所有数学里都表示"估计/预测";`·` = 点积(对应相乘再相加)。
> - **对应代码**:`MatrixFactorization.java:95` —— `mu + bU[u] + bI[i] + dot(p[u], q[i])`。

### 3.1 为什么要三个偏置项

纯靠坐标点积太"干净"了,所以公式里有三个偏移:

| 项 | 含义 | 直觉 |
|---|---|---|
| μ | 全局均值 | "所有人都打 3.5 分"的基线 |
| b_u | 用户偏置 | 这人打分天生苛刻还是宽容 |
| b_i | 物品偏置 | 这部电影公认好还是烂 |
| p_u·q_i | 坐标点积 | 真正的个性化匹配 |

**为什么需要偏置?** 因为"某用户就是爱打高分"这件事和具体电影无关,如果让内积去硬扛它,会学得又慢又差。拆出来之后,内积只需要负责"你和别人不一样的口味",收敛大大加速。这是 Koren 2009 那篇论文的核心贡献之一。

### 3.2 最反直觉的一点:轴不是我们定的

你可能想问:那两个维度到底代表"动作"和"文艺"吗?

**不。这是 MF 最漂亮的地方:这些轴是模型自己从数据里"猜"出来的,没有任何人告诉它,而且通常没有人类能看懂的名字。**

真实的隐藏维度可能是:

- "对 90 年代港片的怀旧"
- "对慢镜头的容忍度"
- "偏爱长片还是短片"
- 某种无法用语言描述的混合模式

你根本列不全,也标不准。所以 MF 干脆不列,让模型自己发现。

> 💡 类比:神经网络的神经元。**没人知道第 37 个维度具体是什么含义**,但它确实在起作用。**别纠结"某个维度代表什么",要看的是整个向量组合起来能不能预测准。**

(想知道这些轴长什么样?[附录 A](appendix/A-mf-visualization.md) 会带你亲手训出 k=2 的品味空间并画成图。)

## 4. 怎么"猜"出这些坐标?—— 教小孩 + 摸黑下山

P 和 Q 全是未知数,怎么求?

### 4.1 白话版:先瞎猜,再微调

就像教小孩认东西:

1. 小孩先瞎说一个答案;
2. 你告诉他错在哪、错了多少;
3. 他往"错得更少"的方向挪一小步;
4. 重复几万遍,越来越准。

MF 也是这么干的。

### 4.2 损失函数:错得有多离谱

只看"已知的那些格子"(用户真正打过分的地方),比较预测分 vs 真实分,差得越多,损失越大。目标就是让这个损失尽量小:

```
L = Σ_{(u,i) ∈ 已观测} (r_ui − r̂_ui)²  +  λ(‖p_u‖² + ‖q_i‖² + b_u² + b_i²)
```

> **🔤 公式翻译**
> - **读作**:"把所有已观测评分上'预测误差的平方'加起来(第一项),再加上一个'惩罚参数太大'的项(第二项)"。这个数越小,模型越好——训练就是把它压低。
> - **没见过的符号**:`‖p_u‖²` = 把 `p_u` 里每个数平方再相加(`Σ p_f²`),衡量"这个向量有多大";`λ`(兰姆达)= 代码里的 `reg`。
> - **对应代码**:误差在 `MatrixFactorization.java:96`(`double e = r.rating() - pred;`);正则体现在更新式的 `- reg * 参数` 里。

第一项:拟合误差。第二项:**正则 λ**(代码里的 `reg`),压制参数大小,防止坐标数字变得巨大、只背下了已知格子却不通用。

### 4.3 梯度下降:摸黑下山

想象你站在一座山上,山下是"损失最小"的谷底。你看不见全貌,但能感觉到脚下的坡度。

- 往下坡方向挪一小步 → 损失变小一点;
- 反复挪,最终走到谷底。

三个旋钮(对应代码参数):

| 旋钮 | 代码 | 白话 |
|---|---|---|
| 学习率 `lr` | `lr` | 步子多大。太大摔下山,太小走不到 |
| 正则 `reg` | `reg` | 别走极端。太大会把坐标压平 |
| 迭代轮数 `epochs` | `epochs` | 来回走几趟。太少没到底,太多会过拟合 |

### 4.4 四条更新式(逐行推导)

**优化方法:随机梯度下降(SGD)**。每次只看一条评分,算出误差 `e = r_ui − r̂_ui`,然后让每个参数沿"让误差变小"的方向走一小步。对上面的损失逐参数求偏导,得到四条更新式(**这就是代码 `MatrixFactorization.java:96-106`**):

```
e_ui = r_ui − (μ + b_u + b_i + p_u·q_i)

b_u ← b_u + η(e_ui − λ b_u)          // η = 学习率 lr
b_i ← b_i + η(e_ui − λ b_i)
p_u ← p_u + η(e_ui · q_i − λ p_u)
q_i ← q_i + η(e_ui · p_u − λ q_i)
```

> **🔤 公式翻译**
> - **共同结构**:`参数 ← 参数 + 步长 × (误差信号 − 正则拉回)`。四行只是把"参数"换成 `b_u / b_i / p_u / q_i`,把"误差信号"换成对应的形式。
> - **`b_u ← b_u + η(e_ui − λ b_u)` 读作**:"用户偏置朝减小误差的方向挪一小步,同时被正则往 0 拉一把"。
> - **`p_u ← p_u + η(e_ui·q_i − λ p_u)` 读作**:"用户隐向量朝物品 `q_i` 的方向走(误差越大走得越多),同时被正则往 0 拉"。
> - **`←`** = "赋值"(就是 Java 的 `=`;数学里 `=` 常表示"相等",所以用 `←` 表示"更新")。**`η`** = 学习率 `lr`。
> - **对应代码**:`MatrixFactorization.java:97-106`(偏置两行 + 隐向量循环两行)。

**为什么 `pu[f]` 的更新要乘 `qif`?** 因为目标是改变 `p·q` = `Σ p_f q_f`。要让内积增加,`p` 就该沿 `q` 的方向走——**梯度里会出现对方的对应分量**。这就是第 1 部 §3 讲的链式法则的模样,不用记,记住"出现对方分量"即可。

**三个容易写错的细节:**

1. **`p_u` 和 `q_i` 必须用彼此的"旧值"更新**。看 `MatrixFactorization.java:101-106`:先把 `pu[f]`、`qi[f]` 存进局部变量 `puf`、`qif`,再用它们算彼此的梯度。如果先更新了 `p_u` 再去更新 `q_i`,就用到了"被污染"的值,SGD 会跑偏。**这是手写 MF 最经典的 bug。**
2. **正则项只压当前参数,不碰误差项**。`− reg * puf` 而不是 `- reg * (e*puf)`。
3. **偏置和隐向量用同一个 η 和 λ**(可分开调,本阶段从简)。

## 5. 训练流程:代码逐段走查

`fit` 在 `MatrixFactorization.java:54-108`,五步:

1. **建索引** `MatrixFactorization.java:55-67`:把稀疏的 `long` userId/movieId 映射成紧凑的 `0..n-1` 下标。为什么要做?因为接下来要把参数存进 `double[]`/`double[][]` **数组**——数组用连续内存 + 下标访问,比 `HashMap<Long, double[]>` 快一个数量级。这是"离线训练要用数组、在线服务才用 Map"的典型分工。
2. **分配参数** `MatrixFactorization.java:68-71`:`bU[nu]`、`bI[ni]`、`p[nu][k]`、`q[ni][k]`。
3. **随机初始化** `MatrixFactorization.java:73-83`:隐向量用均值 0、标准差 `INIT_STD=0.01` 的高斯分布初始化。**为什么要随机且小?** 全 0 初始化会让所有隐向量永远同向(对称性无法打破);太大则初期预测剧烈震荡。
4. **缓存历史** `MatrixFactorization.java:84-86`:仅用于 `recommend` 的兜底判断。
5. **SGD 主循环** `MatrixFactorization.java:88-107`:每个 epoch 先 `shuffle`(打乱顺序,避免"按用户/物品排序的评分"引入相关性导致收敛慢或震荡),再逐条评分更新参数。

### 5.1 参数速查

| 参数 | 代码位置 | 含义 | 本阶段取值 | 调大的后果 |
|---|---|---|---|---|
| `k` | 构造器 | 隐向量维度 | 100 | 表达力↑,内存/时间↑,过拟合风险↑ |
| `epochs` | 构造器 | 遍历全量数据次数 | 50 | 拟合更充分,过多则过拟合 |
| `lr` (η) | 构造器 | 每步走多远 | 0.01 | 太大不收敛,太小训不动 |
| `reg` (λ) | 构造器 | 正则强度 | 0.02 | 太大会把隐向量压平(见 [附录 B §B.2](appendix/B-pitfalls.md)) |

这些取值的来由见 [附录 A 的六个灵魂问题](appendix/A-mf-visualization.md)(INIT_STD 为什么不能是 0、lr/reg 为什么取这个量级)。

## 6. 关键认知:MF 为什么排序弱?

看 `recommend`(`MatrixFactorization.java:131-152`)——它要给**每个未交互物品**算一次分,复杂度 **O(物品数 × k)**。610 用户 × 9724 物品 × 100 维 = 每次评估约 6 亿次浮点运算。**这个复杂度决定了 MF 不适合做全量召回,只适合做候选集上的精排**(第 6 部详细展开)。

但更深层的问题在**目标函数**:MF 最小化的是**已观测评分**的平方误差,它从来没见过"负样本"(用户没评分的物品,可能是没看到,也可能是讨厌)。所以它在排序未观测物品时区分度很差——实测结果:MF 的 RMSE 从 1.13 降到 0.97(预测确实准了),但 HR@10 只有 0.0197,远低于 ItemCF。

**"评分预测准"≠"排得靠前",这是推荐系统最经典的认知鸿沟**,也是第 4 部用 BPR 成对损失要解决的目标错配。

## 7. 本部结论

- MF 把"推荐"从**数数**变成了**学习**:用两个瘦矩阵 `P`、`Q` 逼近那张满是窟窿的大表。
- 它的语言就是第 1 部那套:损失、梯度、lr、reg——**你已经会读它了**。
- 它有两条短板:① 打分复杂度 O(物品数 × k),不适合全量召回;② 目标函数只盯评分,排序能力弱。

第 ① 条是**工程问题**,留到第 6 部用两级架构解决;第 ② 条是**算法问题**,就是下一部的主角。
