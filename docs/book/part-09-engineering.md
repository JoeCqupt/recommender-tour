## 1. 从"跑实验"到"上线"还差什么?

离线实验只管一件事:给定一批测试用户,模型能不能把真实点击的物品排前面?

真实线上服务要管的事多得多:

| 离线实验 | 线上服务 |
|---|---|
| 数据已经切分好,直接读文件 | 用户请求实时进来,特征从哪取? |
| 模型对象在内存里,直接调用 | 训练任务跑完后,模型怎么交给线上? |
| 只看 HR/NDCG | 还要 latency、吞吐、冷启动、A/B 实验 |
| 负样本随便采样 | 线上不能给用户推他已看过的物品 |

阶段五就是来补这些缺口。我们不追求工业级完整度,但要把**主干闭环**跑通。

## 2. 模型导出:为什么训练产物和训练代码要分开?

真实系统里,"训练"和"服务"是两伙人、两台机器、两种生命周期:

- **训练任务**:跑在 GPU/大数据集群上,重、慢、可以失败重跑;
- **在线服务**:跑在 API 机器上,要求低延迟、高可用、快速扩缩容。

所以训练完必须导出一份**服务专用**的轻量产物,线上只读这份产物,不带训练代码。

### 2.1 我们导出三样东西

阶段五导出的目录结构:

```text
models/
├── embedding.store   # BPR 用户/物品向量 + 物品偏置
├── fm.ranker         # FM 的 w0/w/v + 特征索引
└── popular.items     # 热门物品列表(冷启动兜底)
```

| 文件 | 内容 | 对应代码 |
|---|---|---|
| `embedding.store` | 用户向量 Map、物品 ID 数组、物品向量矩阵、物品偏置 | `EmbeddingStore.save()`/`load()` |
| `fm.ranker` | `w0`、一维 `w`、二维 `v`、用户/物品/品类索引 | `FmRanker.saveModel()`/`loadModel()` |
| `popular.items` | 按热度排序的物品 ID 列表 | `RecService.save()` 写入 |

为什么 `EmbeddingStore` 和 `FmRanker` 分开存?因为召回层和精排层本来就是独立演进的。以后召回换成双塔、精排换成 DeepFM,只需要替换各自文件,接口不变。

### 2.2 二进制格式设计

我们用了最简单的 `DataOutputStream` / `DataInputStream`:

- 先写 4 字节 magic(如 `FMRK`)、4 字节 version,方便以后升级格式;
- 再写维度、数组长度等元信息;
- 最后批量写 double/long/int。

这种格式没有通用性(不能给 Python 读),但**教学价值高**:你能打开文件看到每个字段按什么顺序出现,也能算出文件大小验证参数量。

```text
FmRanker 文件大小 ≈ 4 + 4 + 4 + 1 + 4×4 + 8
                  + 8×nu + 8×ni
                  + (字符串长度) × ng
                  + 8×numFeatures + 8×numFeatures×k
                  + 4×ni×平均特征数
```

以 `ml-latest-small` 为例:特征空间 5923 维,`k=32`,模型文件大约 1.5 MB。这个量级甚至可以塞进内存缓存,单次加载毫秒级。

## 3. RecService:把召回、精排、兜底包成一个对象

`RecService` 是阶段五的核心。它上线后只做三件事:

1. **向量召回**:用 `VectorRecall` 从全库物品里捞出 200 个候选;
2. **精排打分**:用 `FmRanker` 或 `BprRanker` 给这 200 个候选打分;
3. **Top-K 截断**:排序后返回前 N 个。

```text
用户请求 → VectorRecall(200) → FmRanker/BprRanker 打分 → Top-N
              ↑
        冷启动用户没有向量 → 直接走 PopularRecall 热门兜底
```

### 3.1 冷启动:没向量怎么办?

训练集里没出现过的用户,`EmbeddingStore.userVector(userId)` 返回 `null`。这时候不能给他算点积,否则返回空列表。

阶段五的兜底策略是:**热门召回**。它的假设是"大多数人爱看的,新用户也有一定概率爱看"。简单粗暴,但不会出幺蛾子。

> 工业界冷启动还会用:内容特征(新物品没有交互,但有类目/标题)、快速在线学习(用户点一个就更新)、热门分层(按地域/时段)。这些在 [第 6 部 §8.2](part-06-two-stage.md) 和 [附录 E](../appendix/E-coldstart.md) 详细展开,阶段五只实现最基础的热门兜底。

### 3.2 A/B 分流:hash(userId) % 2

`RecService` 同时维护两条精排链路:

- **FM 桶**:用特征交叉精排;
- **BPR 桶**:用 BPR 向量精排(和召回同一套向量,作为对照)。

分流按 `userId % 2` 决定进哪个桶。同一个用户永远进同一个桶,保证体验一致;不同用户均匀分到两个桶,可以对比 FM 是否比 BPR 更强。

```java
public String abVariant(long userId) {
    return (userId % 2 == 0) ? "fm" : "bpr";
}
```

> 真实 A/B 实验要配分流比例、样本量计算、指标看板。这里只保留"分流 + 打标"的骨架。

## 4. RecServer:一个零依赖的 HTTP 服务

`RecServer` 用 JDK 内置的 `com.sun.net.httpserver.HttpServer`,不引任何框架。

### 4.1 接口

| 接口 | 说明 | 示例 |
|---|---|---|
| `GET /health` | 健康检查 | `curl /health` |
| `GET /recommend?userId=1&n=10` | 默认 FM 精排 | `curl '/recommend?userId=1&n=10'` |
| `GET /ab?userId=1&n=10` | 按 userId 哈希进 A/B 桶 | `curl '/ab?userId=1&n=10'` |

返回 JSON:

```json
{
  "userId": 1,
  "variant": "fm",
  "latencyMs": 4,
  "items": [1, 2987, 588, 1073, 1196]
}
```

### 4.2 端到端流程

```bash
# 1. 训练并导出模型
mvn -q compile
java -cp target/classes tour.recsys.Stage5Main data/ml-latest-small models

# 2. 启动服务
java -cp target/classes tour.recsys.serve.RecServer models 8080

# 3. 调用(另开终端)
curl 'http://localhost:8080/recommend?userId=1&n=10'
curl 'http://localhost:8080/ab?userId=1&n=10'
```

`Stage5Main` 会先训练 BPR 和 FM,把产物写到 `models/` 目录,然后立即加载回来,给一个测试用户做推荐,验证"导出 → 加载 → 推荐"这个环是通的。

### 4.3 延迟长什么样?

在 `ml-latest-small` 上(约 6000 物品),本地单次请求延迟 2~5 毫秒:

```text
/recommend (FM):  latencyMs ≈ 4
/ab        (BPR): latencyMs ≈ 2
```

BPR 更快,因为它只做向量点积;FM 要累加品类特征,慢一点,但也只有几毫秒。这个延迟对教学 demo 完全够用。

> 真实业务里物品是百万/亿级,召回层不能暴力全扫,要换 ANN 索引(阶段三讲过)。精排层候选固定在几百个,FM/DeepFM 的延迟仍然是可接受的。

## 5. 工程上最容易踩的坑

### 5.1 训练特征和线上特征必须一致

这是线上事故第一大来源。训练时"品类"用了训练集里出现过的 18 个 genre,线上如果突然出现第 19 个 genre,FM 的 `v` 矩阵里没有对应向量,只能忽略或报错。

阶段五的解决方案是:**把特征索引和模型一起导出**。`fm.ranker` 文件里保存了 `userIdx`、`itemIdx`、`genreIdx`,线上加载后完全复用同一套索引。新用户/新物品走冷启动,而不是硬塞进未知索引。

### 5.2 排除已交互物品

训练时我们会把测试集里用户已看过的物品排除;但线上用户刚看完一个电影,下一页推荐应该立刻排除它。这个 `exclude` 集合通常从用户实时行为日志里来,阶段五的 HTTP 接口为了简化没有暴露它,但 `RecService.recommend` 底层已经支持传入排除集合。

### 5.3 模型更新不等于服务更新

训练任务每小时产出一个新模型,但服务不能每小时重启。真实系统会用**滚动加载**:服务进程检测到 `models/` 目录有新版本文件,在内存里重新加载,旧请求继续用旧模型,新请求用新模型,切换过程不中断。

阶段五没有实现滚动加载,但留了一个清晰的入口:`RecService.load(modelDir, candidateSize)`。要加滚动加载,只需要定时调用它替换当前 `service` 实例。

## 6. 阶段五学到了什么?

1. **训练产物必须和服务代码分离**。导出轻量模型,线上不带训练逻辑。
2. **一个推荐服务的核心就是"召回 → 精排 → 兜底"**。`RecService` 把这三件事包在一起。
3. **冷启动不能忽视**。新用户没有向量时,热门兜底是最简单的安全网。
4. **A/B 实验是线上迭代的眼睛**。没有分流,你就不知道新模型上线后到底比旧模型好还是坏。
5. **特征一致性是生命线**。训练时的索引和线上必须是一份,否则模型学到的权重对不上号。
