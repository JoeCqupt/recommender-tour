# 附录 B:踩坑复盘 —— 真实翻车现场

> 这些坑不是"代码写错了",而是**参数/目标的量纲与错配**。
> 它们比正确代码更有价值——因为每一个都对应一个你以后会遇到的陷阱。

---

## B.1 热门惩罚量纲用错,把 ItemCF 召回清零

**现象**:`popAlpha` 默认设成 10 时,**HR@10 = 0.0000**,比什么都不做的 Popular(0.0410)还差。

参数扫描:

| alpha | topK | HR@10 | 覆盖率 |
|---|---|---|---|
| **0.0** | 50 | **0.0541** | 4.5% |
| 0.5 | 50 | 0.0000 | 8.3% |
| 1.0 | 50 | 0.0016 | 2.9% |
| 10.0 | 200 | 0.0000 | 1.7% |

**根因**:`shrink = 1/(1 + alpha·(sqrt(n_j) − 1))`(`ItemCF.java:79`)。`n_j` 是物品被评分次数,热门片能到几百,`sqrt(n_j)` 仍达 ~17,乘上 alpha 后分母爆炸成上百倍。结果**只有"极少人评过"的冷门片能拿到非零相似度**,模型永远只推冷门噪声,留出的热门片一条不命中。

**教训**:任何"惩罚/归一化"项,先算清它的**取值范围**再定系数。一个系数就能把信号全压没。经验做法是先关掉(`alpha=0`)看基线,再逐步加、每步看指标。

**对应章节**:[第 2 部 §4.3](../part-02-itemcf.md)。

## B.2 正则越强 RMSE 越好看,但排序能力归零

**现象**:

| reg | RMSE | HR@10 |
|---|---|---|
| 0.00 | 0.9896 | 0.0197 |
| 0.02 | 0.9664 | 0.0197 |
| 0.05 | 0.9556 | 0.0082 |
| 0.10 | 0.9567 | 0.0000 |

注意到诡异之处:reg 从 0.02 调到 0.10,`RMSE` 越来越"好看"(0.9664 → 0.9567),但 `HR@10` 从 0.0197 直接掉到 **0.0000**。**一个指标在变好,另一个指标在你真正关心的维度上归零。**

**根因**:正则把隐向量 `p_u`、`q_i` 压向 0,模型退化成"只用 μ + b_u + b_i 的偏置模型"。偏置模型预测"安全"(评分总在均值附近),RMSE 好看;但它**丢掉了所有个性化排序信号**,HR 归零。

**教训**:离线指标的"最优"取决于你优化哪个目标。调参时永远盯着你真正要的指标,别被一个好看的 RMSE 骗进"上线后毫无个性化"的坑。

**对应章节**:[第 3 部 §5.1](../part-03-mf.md)、[第 5 部 §4](../part-05-evaluation.md)。

## B.3 把"所有评分"当正样本,BPR 反而更差

**现象**:一开始没有 `filterRatings(4.0)`,直接把全部 10 万条评分当隐式正样本训练 BPR,结果 HR@10 只有 2.46%,还不如 ItemCF。

**根因**:3 分、2 分甚至 0.5 分的评分,对用户来说未必是"喜欢"。把它们当正样本,等于告诉模型"用户喜欢《某烂片》",负采样时再随便抽个没看过的电影说"这个不如《某烂片》"。标签本身就脏了,模型当然学不好。

**教训**:隐式反馈的"正样本定义"是业务问题,不是技术问题。MovieLens 里用 ≥4.0 当"喜欢"是领域惯例,但真实业务里可能需要结合播放完成率、停留时长、是否收藏等行为来定义。

**对应章节**:[第 4 部 §8](../part-04-bpr.md)。

## B.4(经典 bug)p_u 和 q_i 不用旧值更新,SGD 会跑偏

**现象(代码层面)**:更新隐向量时,如果先更新了 `p_u` 再更新 `q_i`,`q_i` 就用到了"被污染的 `p_u`",梯度算错。

```java
// ❌ 错误写法
for (int f = 0; f < k; f++) {
    pu[f] += lr * (e * qi[f] - reg * pu[f]);   // 先改了 pu[f]
    qi[f] += lr * (e * pu[f] - reg * qi[f]);   // 这里读到的是新 pu[f]!
}

// ✅ 正确写法(MatrixFactorization.java:101-106)
for (int f = 0; f < k; f++) {
    double puf = pu[f];   // 先存旧值
    double qif = qi[f];
    pu[f] += lr * (e * qif - reg * puf);
    qi[f] += lr * (e * puf - reg * qif);   // 用的是旧 puf
}
```

**根因**:`p_u` 和 `q_i` 的梯度互相依赖对方。必须用彼此的**旧值**(同一时刻的快照)一起算,才是这一轮正确的梯度。

**教训**:**手写 MF 最经典的 bug**。凡是"两个互为参数的变量要同时更新",都要先存快照。BPR 的"三方拉扯"同理(`BprMF.java:113-127` 里先存 `puf/qif/qjf`)。

**对应章节**:[第 3 部 §4.4](../part-03-mf.md)、[第 4 部 §4.3](../part-04-bpr.md)。

## B.5(同一只 bug,换了张脸)FM 的交叉项梯度也要用旧值

**现象(代码层面)**:FM 的交叉项 `Σ⟨v_i, v_j⟩` 对 `v_f` 的梯度是 `Σ_{g≠f} v_g`——它是**所有其它激活向量之和**。如果一边遍历特征、一边更新 `v`,再一边累加这个和,梯度就会用到"已经改过一半"的向量。

```java
// ❌ 错误写法:sum 边更新边累加,梯度被污染
for (int f : s) {
    for (int d = 0; d < k; d++) sum[d] += v[f][d];   // 混入了新值
    for (int d = 0; d < k; d++) v[f][d] -= lr * g * (sum[d] - v[f][d]);
}

// ✅ 正确写法(FmRanker.java:199-215):先用旧值把 sum 算完,再统一更新
double[] sum = new double[k];
for (int f : s) {
    for (int d = 0; d < k; d++) sum[d] += v[f][d];   // 全是旧值
}
for (int f : s) {
    for (int d = 0; d < k; d++) v[f][d] -= lr * (g * (sum[d] - v[f][d]) + reg * v[f][d]);
}
```

**根因**:和 B.4 一模一样——`v_f` 的梯度依赖**其它所有 `v_g`**,必须用同一时刻的快照。

**教训**:从 MF 的"两方"到 BPR 的"三方",再到 FM 的"全体",坑的形状在变,**本质永远是"梯度用了不该用的新值"**。手写任何基于梯度的模型,先问一句:这次的梯度依赖谁?它们更新了吗?

**对应章节**:[第 7 部 §4.3](../part-07-ctr.md)。

## B.6 跨坑总结:三个"指标骗人"的坑

把 B.1、B.2 和第 6 部的"候选集越大越好"放在一起看,它们是同一个道理:

| 坑 | 指标怎么好看 | 为什么实际没用 |
|---|---|---|
| 正则越强 | RMSE 更好 | 排序能力归零 |
| MF 的 RMSE 低 | 预测更准 | 它只优化已评分的格子 |
| 候选集开大 | 召回率暴涨 | 弱精排下 HR 反而降 |

**一句话**:每个指标只考核一件事。**调参时盯着你真正要的那个,别被一个好看的数字骗。**
