# 第 6 部 召回 + 精排:两级架构 &nbsp; `⚙️ 工程/系统`

> 第 4 部结束时留下一句话:"BPR-MF 是 O(物品数 × k) 的全量打分,适合精排,不适合全量召回。"
> 这一部就是把这句工程结论,做成真正的推荐服务主干——**它首先解决的是算力,不是效果。**

**前置知识**:第 3–4 部(MF/BPR 的打分复杂度)、第 5 部(评估指标)。
**读完你能**:说清"召回漏掉的,精排永远救不回来",能画出一个多路召回的架构图,理解"两级不一定比单级好"。
**对应技术象限**:⚙️ 工程/系统(架构本身不是模型;但向量召回仍复用 🔵🟣 学出的 embedding)。
**源码**:`recall/`、`model/Ranker.java`、`serve/EmbeddingStore.java`、`Stage3Main.java`。

---

## 1. 为什么单级模型撑不起线上

假设有 1 亿物品、向量维度 100:

- 给一个用户打分,就要算 1 亿次 100 维点积 ≈ 100 亿次浮点乘加;
- 一个请求这么慢,还要乘以 QPS。

结论:**没有任何线上系统会"拿模型扫全库"。** 正确做法是先用一个便宜的手段从 1 亿里捞出几百个候选,再用贵模型对这几百个精细排序。这就是**召回(recall)→ 精排(rank)**两级架构。

一句话概括二者分工:

| | 召回 | 精排 |
|---|---|---|
| 目标 | 快、全,别漏 | 准,把好的排前面 |
| 处理对象 | 全库 → 几百个候选 | 几百个候选 → Top-K |
| 允许的误差 | 可以粗、可以近似(ANN) | 尽量精 |
| 常见手段 | 多路并行(热门/ItemCF/向量) | 单个强模型(BPR-MF / CTR) |

```text
                    │  (并行, 快)  │  ItemCF召回    ├─► 合并去重 ─► 候选集(几百个)

                    ┌─────────────┐                   ▼
                    │  精排 (慢,准) │ ◄──── BPR-MF / Ranker 给每个候选打分
                    └─────────────┘

                                                      ▼
                                                   Top-K
```

## 3. 代码结构

| 文件 | 职责 |
|---|---|
| `recall/Recall.java` | 召回层统一接口:`recall(userId, n, exclude)` |
| `recall/PopularRecall.java` | 热门召回(兜底路,必挂) |
| `recall/RecommenderRecall.java` | 适配器:把任意 `Recommender` 当一路召回用 |
| `recall/VectorRecall.java` | 向量召回:用户向量 × 物品向量,暴力全扫 + 小顶堆 Top-N |
| `recall/MultiRecall.java` | 多路合并:轮询取各路候选,去重 |
| `model/Ranker.java` | 精排打分接口:`score(userId, movieId)` |
| `serve/EmbeddingStore.java` | 训练产物导出为"线上形态"(只有向量,没有训练逻辑) |
| `recall/TwoStageRecommender.java` | 两级主干:召回 → 精排 → Top-K,实现 `Recommender` 复用评估框架 |
| `Stage3Main.java` | 本阶段实验入口 |

**两个值得记住的设计:**

1. **`RecommenderRecall` 点破了一件事**:一个能吐 Top-N 的模型,把它的 Top-N 当候选集,它就是一路召回。"单级模型"和"一路召回"只是同一个东西的两种视角——所以第 2/4 部的 `ItemCF` 一行不改就挂进了多路召回。
2. **`EmbeddingStore` 是"离线训练 → 在线 serving"的最小示范**:训练任务跑完把 `p`/`q` 写进它(真实系统里是推给向量服务),线上只做查表和点积。`fromBpr(model)` 就是这一步导出。

## 4. 召回率天花板

先看各路召回的"召回率"——**真实测试物品有多大概率落进候选集**。这是最重要的概念,因为精排只能在候选集里排序,召回没捞到的东西,精排永远排不出来。

`Stage3Main` 输出(每路取 200 个候选,多路合并取 600):

| 召回通道 | 召回率 | 平均候选数 |
|---|---|---|
| PopularRecall | 25.8% | 200 |
| ItemCF召回 | 27.3% | 198 |
| VectorRecall | 36.9% | 200 |
| MultiRecall | 45.2% | 394 |

读法:

- 单路召回里**向量召回最强**(36.9%)——因为 BPR 的 embedding 就是在学"用户可能喜欢什么";
- **多路合并 > 任何单路**(45.2%):三条路各补各的盲区(热门兜底、ItemCF 抓共现、向量抓语义),这正是多路召回存在的理由;
- 召回率给精排设了**上限**。想提升整体效果,第一步往往不是换更强的排序模型,而是**先把召回率提上去**。

## 5. 候选集开多大?——一个反直觉的结论

候选集大小是个关键超参。直觉上"候选越多,好东西越不容易漏",但实验给出两个方向相反的表。

**表2:召回=向量,BPR 精排用同一套向量**

| 候选数 | 召回率 | HR@10 | NDCG@10 | 评估耗时 |
|---|---|---|---|---|
| 50 | 14.9% | 0.0438 | 0.0205 | 210ms |
| 100 | 24.4% | 0.0438 | 0.0205 | 221ms |
| 200 | 36.9% | 0.0438 | 0.0205 | 226ms |
| 500 | 55.5% | 0.0438 | 0.0205 | 306ms |
| 1000 | 69.2% | 0.0438 | 0.0205 | 435ms |

召回率从 14.9% 涨到 69.2%,**HR@10 却纹丝不动**。为什么?

因为这里召回和精排用的是**同一套向量**:精排给候选打的排序 = 召回时的顺序。所以最终 Top-10 就是"全库 BPR 打分的前 10 名"里落在候选集内的那几个——只要候选集够大装下真正的前 10,再开大也没有新东西进来,只是白花时间。**这种情况下两级 == 单级,架构只省算力,不改质量。**

**表3:把精排换成"热门分"(一个和向量召回不一致的弱精排)**

| 候选数 | 召回率 | HR@10 | NDCG@10 | 评估耗时 |
|---|---|---|---|---|
| 50 | 14.9% | 0.0382 | 0.0182 | 181ms |
| 100 | 24.4% | 0.0340 | 0.0164 | 191ms |
| 200 | 36.9% | 0.0315 | 0.0155 | 219ms |
| 500 | 55.5% | 0.0296 | 0.0149 | 311ms |
| 1000 | 69.2% | 0.0295 | 0.0149 | 438ms |

这次 HR **随候选数下降**,而且 `n=1000` 时精确跌回 Popular 基线的 0.0295——相当于两级退化成"纯推热门"。

原因:候选池越大越接近全库,弱精排(热门)就越无力在其中做个性化。反过来看,候选越小,反而是"向量召回"这半边在小池子里兜住了个性化。

**两条结论,比"两级更好"更重要:**

1. **召回与精排是接力,两棒要匹配。** 弱精排靠"小而准"的候选集兜个性化(候选越小越好);强精排需要"大候选池"把用户真实喜欢的物品捞进来才排得出(候选越大越好)。所以候选集大小不能拍脑袋定,要配合精排的强弱来调。
2. **"两级一定比单级好"是错觉。** 精排比召回强,两级才有效;否则只是把召回的结果重算一遍,白绕一圈。表2 就是活证据。

## 6. 单级 vs 两级总账

| 方案 | HR@10 | NDCG@10 | 覆盖率 | 评估耗时 |
|---|---|---|---|---|
| Popular | 0.0295 | 0.0149 | 1.0% | 2ms |
| ItemCF | 0.0396 | 0.0186 | 10.8% | 156ms |
| BPR-MF(k=100)(单级:扫全库) | 0.0438 | 0.0205 | 15.3% | 587ms |
| 两级(MultiRecall→600→精排) | 0.0438 | 0.0205 | 15.3% | 445ms |
| 两级(VectorRecall→200→精排) | 0.0438 | 0.0205 | 15.3% | 225ms |

- **效果上:两级 = 单级**(原因见 §5 表2),因为精排和召回是同一个模型;
- **耗时上**:两级只给 200 个候选打分,单级给全库 6千+ 打分。本数据集物品少,差距不明显;物品上亿时,这就是**能不能上线的分水岭**。

## 7. 工程实践:让召回真正快起来

`VectorRecall` 是**暴力全扫**(逐个物品算点积),复杂度 `O(物品数 × k)`。它准,但不快。物品上亿时,工业界用**近似最近邻检索(ANN)**把它换掉:

| 方案 | 思路 | 特点 |
|---|---|---|
| IVF | 先把向量聚类成若干桶,查询时只扫最近的几个桶 | 实现简单,召回率损失小 |
| HNSW | 构分层图,像跳表一样在图上贪心找近邻 | 查询快,内存高,建索引慢 |
| LSH | 用哈希把"可能相近"的向量分到同一桶 | 理论优雅,实践中召回率一般 |

**核心思想**:牺牲一点点召回率,换来数量级的加速。这正好呼应 §4——召回率是天花板,ANN 会把这个天花板压低一点,但换来线上可用。

实现上还有一个细节:`VectorRecall` 没有"全排序再截断",而是用**大小为 n 的小顶堆**一次扫描求出 Top-N,复杂度 `O(物品数 × log n)`,比全排序的 `O(物品数 × log 物品数)` 更省。这是处理流式候选的标准写法。

## 8. 冷启动与离线 → 在线 serving

### 8.1 离线训练 → 在线 serving 的拆分

`EmbeddingStore`(`serve/EmbeddingStore.java`)演示了整条链路的骨架:**离线用全量数据训练,产出 `P`、`Q` 两组向量;线上只做查表和点积,不含任何训练逻辑。**

```text
离线训练学模型  →  产出 P、Q 矩阵        (训练任务,Spark/Flink,周期跑)
        │
        ▼
线上服务只查表/打分  →  召回 + 精排        (低延迟,高 QPS)
        │
        ▼
新物品/新用户用兜底策略  →  内容模型 / 热门 / 偏置
```

理解了这个拆分,你就从"会写 MF 代码"迈进了"能设计推荐服务"的门槛。

### 8.2 物品冷启动:新物品没有 embedding 怎么办

新物品(新上架的商品/新上的电影)没有历史交互,自然学不出 `q_i`。代码里已经做了最简单兜底:

```java
Integer i = itemIdx.get(movieId);
if (i == null) {
    return mu;  // 没见过的新物品,只能退化成全局均值
}
```

真实业务里通常有三种策略,复杂度和延迟递增:

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **1. 定时离线重训**(最常见) | 每天凌晨跑训练,产出新 `P`、`Q` 推给线上向量服务 | 稳定、可复现、好维护 | 新物品要等下次训练,有小时级到 T+1 延迟 |
| **2. 内容特征冷启动** | 用标题/类目/标签等 metadata,经内容模型预测一个"初始 `q_i`" | 新物品立刻有向量 | 需要额外训练一个内容模型 |
| **3. 在线学习 / 流式更新** | 有新交互就用 SGD 增量更新参数 | 延迟最低,快速融入 | 工程复杂,易受噪声/欺诈点击影响,参数可能漂移 |

小公司/初期项目一般用策略 1;中等规模会加策略 2 做冷启动兜底;大厂才会做策略 3。这套东西到了阶段 5(工程与服务)会系统化展开。

## 9. 本部最重要的结论

1. **两级架构的本质是"用便宜的召回缩小战场,把贵模型留给少数候选"。** 它首先解决的是**算力/延迟**,不是效果。
2. **效果要提升,精排必须和召回"不一样、且更强"。** 如果精排只是把召回重算一遍,两级等于单级(§5 表2)。
3. **召回率是精排的天花板。** 优化整体效果时,先看召回率;瓶颈在召回,换多强的排序模型都没用。
4. **候选集大小要配合精排强弱来调**,不是越大越好(§5 表3)。

这也直接指向下一步:**让精排成为"真正不同的模型"**——引入用户/物品/上下文的交叉特征做 CTR 估计,这才是工业推荐效果提升的主战场。而这类模型的特征工程与训练生态,自然要换到 Python。
