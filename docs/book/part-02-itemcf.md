## 0. 先摆正坐标:推荐系统在干什么

在写任何算法前,先换掉 CRUD 的心智。

CRUD 的心智是:"给定 ID → 查/改一条记录,对错二元"。推荐系统的心智是:

> 给定一个用户(和上下文)→ 给整个候选物品集合打分 → 排序 → 取前 K 个。
> 没有"正确答案",只有统计指标;模型是"估计器",不是"查询器"。

本书前两个算法,恰好覆盖两种截然不同的"打分"哲学:

| | ItemCF(第 2 部) | 矩阵分解 MF(第 3 部) |
|---|---|---|
| 打分依据 | **数出来**的:共同用户多的物品更相似 | **学出来**的:用梯度下降拟合一个低维隐空间 |
| 需要训练吗 | 几乎不用(统计共现即可) | 需要,迭代优化 |
| 擅长 | 召回 / Top-N 排序 | 评分预测(也能排序) |
| 单次打分复杂度 | O(用户的 topK 邻居) | O(隐维度 k) |
| 本质 | 记忆型(memory-based) | 模型型(model-based) |

理解这张表,就理解了这场"从统计到学习"的演进。

## 1. 共享地基:倒排索引与统一接口

本书所有算法都建立在同一层抽象上,先花两分钟看懂它,后面会一直复用。

### 1.1 `Dataset` 为什么要把索引建好

CRUD 里你可能习惯"有一个 `ratings` 表,要查就 `where user_id=?`"。推荐系统里这样查会慢到不可用,所以 `Dataset`(`data/Dataset.java`)在构造时就把索引建好:

- `byUser`:userId → 该用户的所有评分(`ratingsOfUser`)
- `byItem`:movieId → 该物品的所有评分(`ratingsOfItem`)
- `globalMean`、`maxTimestamp` 等派生量

**为什么重要**:ItemCF 要"哪些用户评过这部电影",MF 要"某用户评过什么"——都是高频查询。提前建索引把查询从 O(N) 降到 O(结果数)。这是你熟悉的"以空间换时间",只是对象换成了推荐数据。

`itemsOfUser(userId)` 返回 `Set<Long>`,后面评估时的"已见物品要去掉"就靠它。

### 1.2 统一接口 `Recommender`

```java
List<Long> recommend(long userId, int topN, Set<Long> exclude);
```

三个参数就是推荐系统的通用签名:**给谁、要几条、排除什么**。`exclude` 通常是用户训练集里已交互过的物品(线上还要排除已曝光的,这涉及位置偏置,第 6 部再谈)。

**设计意图**:所有算法实现同一个接口,`Main` 和 `Evaluation` 就能对它们一视同仁地跑评估、出对比表。你新增 BPR、甚至未来的 DIN,都只要实现这个方法,评估代码一行不用改。这是"面向接口"在算法迭代里的价值——**让不同算法可比较**。

## 2. ItemCF 的直觉(先别看公式)

你看过《玩具总动员》,系统发现"看过《玩具总动员》的人大多也看了《虫虫危机》",于是把《虫虫危机》推给你。**两个物品被同一批用户喜欢,它们就相似** —— 就这么简单。

注意它推荐的是**物品**,不是"和你相似的人用了什么"。这是 ItemCF 和 UserCF 的分水岭(见 §5)。

---

## 3. 数学:余弦相似度

把每个物品表示成一个"用户集合":

```
U_i = 喜欢物品 i 的用户集
```

两个物品的相似度用集合的**余弦相似度**:

```
sim(i, j) = |U_i ∩ U_j| / sqrt(|U_i| · |U_j|)
```

- 分子 `|U_i ∩ U_j|`:同时喜欢 i 和 j 的用户数(两者"共现"的次数)。
- 分母 `sqrt(|U_i|·|U_j|)`:归一化,防止"热门物品和谁都有共同用户"导致相似度虚高。

> **🔤 公式翻译**
> - **读作**:"同时喜欢 i 和 j 的人数,除以 i、j 各自受欢迎程度的几何平均"。分子越大越相似,分母把"热门"的影响除掉。
> - **没见过的符号**:`|U_i|` = 集合 `U_i` 里元素个数(就是 `Set.size()`);`sqrt` = 开平方。
> - **对应代码**:`ItemCF.java:78` —— `cos = c.getValue() / (ni * itemNorm.get(j))`(`c.getValue()` 是分子,`ni * itemNorm.get(j)` 是分母)。

给用户 u 推荐时,拿他历史喜欢的每个物品 i,把 i 的相似物品的相似度**累加**到候选物品上:

```
score(u, c) = Σ_{i ∈ I_u} sim(i, c)
```

> **🔤 公式翻译**
> - **读作**:"对用户 u 历史里的每个物品 i,把'它和候选 c 的相似度'全部加起来,当作候选 c 的总分"。
> - **没见过的符号**:`Σ` = 求和(一个 for 循环);`I_u` = 用户 u 历史交互过的物品集合。详见 [第 1 部 §1.3](part-01-math.md)。
> - **对应代码**:`ItemCF.java:98-110` 的双层循环,核心是 `ItemCF.java:108`:`score.merge(cand, nb.getValue(), Double::sum)` —— 把邻居相似度累加。

分数最高的若干物品就是推荐结果。**这就是"召回/排序"里打分的雏形**:候选集 = 历史物品的相似物品,分数 = 相似度累加。

## 4. 三个工程决策(这才是实现的重点)

公式谁都能写,能跑在 10 万条数据上才是本事。代码里有三处关键取舍:

### 4.1 用倒排索引两两配对,而不是物品两两盲扫 —— `ItemCF.java:57-69`

朴素做法是"对任意两个物品算相似度",复杂度 O(items²) = 9724² ≈ 9500 万对,大部分是 0(没有共同用户),纯浪费。

正确做法:**遍历每个用户评过的物品,两两配对累加共现次数**。复杂度变成 O(Σ_u |I_u|²)——只看真实存在共现的对。代码里 `coCount` 就是"共现次数矩阵"的稀疏表示(`Map<物品, Map<物品, 次数>>`)。

> 这是整个 ItemCF 最核心的一行工程直觉:**从"问所有物品对"改成"问所有用户"**。你的数据是稀疏的,就让循环只走非零的部分。

### 4.2 只保留每个物品的 topK 邻居 —— `ItemCF.java:71-88`

一个热门片可能和上万个物品有共现。全存下来,`sim` 会爆炸,而且长尾邻居多是噪声。所以每个物品只留最相似的 `topKNeighbors` 个(`ItemCF.java:84`)。这既省内存,又天然过滤噪声。

### 4.3 热门惩罚(相似度收缩) —— `ItemCF.java:79`

```java
double shrink = 1.0 / (1.0 + popAlpha * (itemNorm.get(j) - 1.0));
```

`itemNorm.get(j)` 是 `sqrt(|U_j|)`。想法是:越热门的物品,相似度打越狠的折,避免"因为热门被所有人看了"就误判为相似。

**但这里的公式量纲是错的** —— `popAlpha` 默认设成 0,即关掉惩罚。这段代码留作"实验旋钮",不是"开箱即用"。翻车过程见 [附录 B §B.1](appendix/B-pitfalls.md)。

## 5. 推荐阶段:代码逐段走查

`recommend` 在 `ItemCF.java:91-118`,四步:

1. `ItemCF.java:93-96` 取出该用户的历史物品;没有历史就返回空(冷启动,本阶段不处理)。
2. `ItemCF.java:97-110` 遍历历史物品,把每个邻居的相似度累加到 `score`。**注意 `ItemCF.java:105`**:累加前先按 `exclude` 过滤掉用户已看过的,避免推荐已经看过的电影。
3. `ItemCF.java:111-112` 对候选按分数降序排序。
4. `ItemCF.java:113-117` 截取前 topN。

有一个容易被忽略的细节:为什么第 2 步不会推荐"用户自己历史的物品"?因为相似度矩阵里 `sim(i,i)` 不存在(co-count 只记录 i≠j 的对),加上 `exclude` 兜底。**这个"不自指"性质是 ItemCF 的结构保证**,不需要额外去重。

## 6. 为什么工业界偏爱 ItemCF 而不是 UserCF

- **物品比用户稳定**。商品一旦上架,它的相似关系相对固定,可以离线算好、缓存,在线只查表;而用户兴趣天天变,UserCF 的邻居要频繁重算。
- **可解释**。"因为你看过 A、B" → 推荐 C,理由明确。
- **复杂度更友好**。物品数通常远小于用户数,相似度矩阵规模可控。

代价:ItemCF 依赖**较强的共现**,数据极度稀疏(长尾物品没人一起看)时会失效。这时就需要 MF 这种"泛化"能力更强的模型。

---

## 7. 复杂度小结

| 阶段 | 复杂度 | 说明 |
|---|---|---|
| 训练 | O(Σ_u \|I_u\|²) | 配对共现;ml-latest-small 上毫秒级 |
| 训练 | O(#items · avgNeighbors · log) | 邻居排序取 topK |
| 单次推荐 | O(\|I_u\| · topK) | 只碰历史物品的邻居,与全量物品数无关 |

**最后一行的意义**:ItemCF 的单次推荐**不随物品总数线性增长**,这正是它适合做**召回**的原因。记住这一点,第 6 部搭两级架构时会用到。

## 8. 本部的结论

ItemCF 是"统计时代"的代表:**它不学习,它只数数**。

它有一个致命弱点:真实数据极度稀疏(610 用户 × 9724 物品,只有 10 万条评分,密度约 1.7%),绝大多数物品对**从来没有共现过**,这时 ItemCF 的相似度就是 0,束手无策。

> 现实的评分矩阵几乎全空,而 ItemCF 只会"数已经填了的格子"。**怎么猜出那些从没一起出现过的关系?** 这就要请出第 3 部的主角——矩阵分解。
